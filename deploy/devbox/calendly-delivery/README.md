# Calendly runtime delivery proposal

Source only. Do not run the staging helper, change GitHub secrets, dispatch a workflow, invoke the installer, restart a service or contact the provider without separately approved scope. This design does not clear existing installer, migration, authentication, provider-hook or deployment holds. The existing deployment workflow is a mutating full carrier, not a read-only or config-only operation.

The concrete path is secure-form delivery into the authorized operator workspace environment, then explicit promotion into the existing GitHub `devbox` environment secrets, then the workflow's explicit job environment mapping, then `configuration` / `deliver_configuration` into protected `secrets.env`, then the separately reviewed installer runtime passthrough into0700 directory /0600 `runtime.env`, readonly mounted at `/run/superserve/console.env` and sourced before Next. Workspace environment variables are not automatically visible in GitHub Actions. An approved GitHub identity with environment-secret write authority is required; if unavailable, stop rather than create credentials or widen access.

The proposed promotion helper accepts only `CALENDLY_API_TOKEN`, `CALENDLY_ORGANIZATION_URI`, and `CALENDLY_ENTERPRISE_EVENT_TYPE_URI`. Default mode validates presence and refuses writes. An explicit future `--apply-github-secrets` operation uses the existing authenticated gh client, fixed repository/environment and `DEVBOX_SECRET_` names. Values travel on stdin, never arguments or output; stderr is discarded. All values are validated before the first write. GitHub writes are not atomic: a partial/timeout/interruption stops with names only and must be reconciled before another attempt. There is no automatic retry, deletion, rollback or dispatch. Review the actual gh identity/permissions and secure-form delivery binding before approving this operation. Do not run with shell tracing, verbose HTTP debugging or untrusted credential helpers. No credentials are provided by this source.

The workflow maps those three GitHub environment secrets explicitly to `DEVBOX_SECRET_*`. Existing secret-prefix serialization removes that prefix and shell-quotes values. The Calendly set may be entirely absent to preserve existing deployments; partial configuration fails before delivery. Existing unrelated protected secrets must remain present in the approved workflow because `deliver_configuration` replaces the complete file, not a patch of three keys. It also writes other configuration and deployment metadata as part of normal deploy; do not represent this source as a safe independent config-only carrier.

`GOOGLE_SIGNUP_PROOF_SECRET` is intentionally absent from promotion and workflow mappings. It remains in the existing on-box console-secrets file. The parent runtime patch refuses configured Calendly rollout when that existing proof is missing/short, before generation or installer mutations. It must not be rotated, exported or logged. URI/token presence is not provider validation. Later authorized validation must check organization/event-type binding and permitted scheduled-events/invitees GETs using booleans only. No provider write/webhook or database migration is included.

The source image rebuild does not need Calendly credentials. Runtime configuration requires a separately approved controlled Console start after the correct consumer source is assembled. Do not execute the historical install-ui tail as a shortcut: its existing smoke/calendar hooks and broader holds are independent. Actual runtime presence, permission, binding and UI QA remain pending until separately measured.
